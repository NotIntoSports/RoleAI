# 0004 — 级联与端到端 Realtime 双模式并存

- 状态：已采纳
- 日期：2026-08-31 起（Realtime 适配）、2026-09 下旬（全双工改造完成）

## 背景

语音对话有两条技术路线：

- **级联**：ASR → LLM → TTS 三段独立 HTTP 请求。灵活（三段可混搭任意供应商）、可解释（哪段失败看得见），但每轮是"存-转-发"，延迟是三段之和。
- **端到端 Realtime**：一条 WebSocket 全双工长连接，模型直接听音频、流式吐语音。延迟低（说完→出声约一秒内）、可打断，但绑定支持该协议的服务商。

## 选项

1. **只做级联**——体验天花板低。
2. **只做 Realtime**——把用户锁死在少数服务商上，且当时（2026-08）各家 Realtime 的方言差异大、可用性参差。
3. **双模式并存，按线路选择**：语音线路是级联还是 Realtime 由用户在服务页配置；两条路线共享同一套会话状态机、记录与纪要。

## 决策

选项 3。Realtime 侧把供应商差异（OpenAI、阿里云 DashScope、智谱）收敛成协议方言层 + 能力画像，新增供应商 = 加一份方言；级联侧保持"完全不动"的原则独立演进（有界重试等改进见 [0008](0008-hand-written-retry.md)）。全双工改造的核心原则：**音频热路径上没有会被业务逻辑长期持有的锁**，细节见[实时语音管线](../realtime-voice-pipeline.md)。

## 后果

- 好处：用户按预算与网络自主选择；Realtime 故障时可切级联继续用；两条路线互相作为对方的回归参照。
- 代价：会话编排要同时伺候两种轮次语义（级联的"请求-响应"与 Realtime 的"事件流"），编排层复杂度高。
