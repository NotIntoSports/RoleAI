# 0001 — 从多进程架构收敛为单一 Tauri 应用

- 状态：已采纳
- 日期：2026-08（重构期间按页面逐阶段迁移、逐阶段验收，最终合并为单一产品路径）
- 决策人：项目维护者

## 背景

项目最初是一条多进程产品线：Electron + Rust 客户端、Next.js 管理端、Go Control API、Python Agent 各自独立进程，配合数据库与 nginx。对一个本地语音助手来说，这条链路带来了致命的复杂度：

- 用户要跑 4~5 个进程才能得到一次语音回答，任何一环挂掉都是"连不上"而不是可解释的错误；
- 部署要装数据库、配服务、起网关，"本地优先"名存实亡；
- 每条进程边界都是一次序列化 + 一次故障点 + 一份配置。

## 选项

1. **保留多进程架构，修补可靠性**——继续背着部署与联调成本。
2. **收敛为单一 Tauri 2 应用**：Rust 承载全部业务，WebView 只跑界面，音频子进程按需拉起。
3. **Electron + Node 单进程重写**——音频实时性（VAD 每窗推理、PCM 泵）在 Node 的事件循环模型里做不好。

## 决策

选项 2。迁移按页面逐阶段进行（壳层 → 设置 → 资料 → 级联会话 → …），每阶段有验收记录后才切流量；Go Control API、Python Agent、Next.js 管理端、登录体系全部移除，仓库只保留一条 Tauri 产品路径。

## 后果

- 好处：安装即用（一个安装包 + 可选虚拟声卡）；无登录、无服务器；语音管线与 UI 在同一进程内通信，音频热路径上不再有跨进程序列化。
- 代价：Rust 侧业务代码体量大（含约 3000 行的会话编排模块）；WebView 与 Rust 的类型契约需要工具维持（见 [0007](0007-ts-rs-type-contracts.md)）。
- 遗留：会议音频采集无法在纯 Rust 里稳妥完成，由独立的 C# 子进程承担（见 [0006](0006-csharp-audiobridge.md)）。
