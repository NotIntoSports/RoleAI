# 用 Rust 做一个全双工实时语音助手：断句、回声与打断

> 本文是 RoleAI 技术系列的第一篇。RoleAI 是一个本地优先的 Windows 实时语音 AI 角色助手（Rust + Tauri），用来做模拟面试训练、会议助手和直播讲解。文中所有数字都来自仓库里的基准与评测报告，可一键复现；测试环境为 Intel Core Ultra 7 255H / Windows 11（10.0.26200）/ rustc 1.96.0，2026-09-30。

实时语音对话里最难的不是调模型——ASR、LLM、TTS 都有现成服务——而是三个"什么时候"的问题：

1. 用户**什么时候说完了**？（断句）
2. AI 播报时，怎么不把扬声器的声音**当成用户在说**？（回声）
3. AI 说到一半，用户插话了，**怎么知道、怎么接**？（打断）

这三个问题共享同一个约束：你的处理预算只有一帧音频的时间。RoleAI 以 32 ms 为块接收麦克风数据，任何一环慢过这个间隔，队列就会越积越长。做完这个项目后我们的结论是：音频热路径根本不是瓶颈——真正咬人的是状态机和阈值。

## 一、断句：两级检测，各答一个问题

流式对话的第一步是知道"这一句说完了"，才能提交识别、触发回答。判早了，用户句中停顿换口气就被抢答；判晚了，每轮对话都拖着一段尴尬的沉默。

只靠一个信号都不够：

- **音量/概率阈值（VAD）**便宜，但只能回答"有没有人在出声"，回答不了"这句话完整吗"。"嗯……让我想想"里有两个很长的停顿，但那不是句尾。
- **语义完整度模型**能理解句子，但要跑一次神经网络，不可能每个 32 ms 窗都跑一次。

所以 RoleAI 用两级串联，各自回答一个问题：

1. **Silero VAD 判「在说话」**：16 kHz 采样，512 采样一窗（正好 32 ms），输出窗口含人声的概率。话语分段器在这之上做状态机：20 ms 一帧，连续 3 帧（60 ms）人声判定开口，35 帧（700 ms）静音判定收尾，同时要求最少 200 ms 语音（防咳嗽误触发）、单句上限 25 秒、开头保留 200 ms 预滚（别把第一个字切掉）。
2. **Smart Turn 判「说完了」**：pipecat-ai 的 smart-turn-v3 模型（ONNX int8 量化，约 8.7 MB，随应用打包），输入最近 8 秒音频的 Whisper 对数梅尔特征，输出"这个回合完成了吗"的概率，阈值 0.5。它只在 VAD 判定静音、分段器准备收尾时出场，每轮最多一次，而不是每窗都算。

两级配合的价值有多大？我们做了一套离线评测（合成面试回答语料、按 32 ms 实时帧喂给生产代码，复现命令见[评测报告](../reports/audio-eval.md)）：在"句中犹豫"场景里，**只用 VAD 的过早截断率是 50%，加上 Smart Turn 降到 25%**，且被截断的那半句从"立即截断"（1.8 ms 后落句）改善到约 1 秒——被挽回的正是"嗯……"之后那半句真话。

代价可控。Criterion 基准显示（[报告](../reports/benchmarks.md)）：Silero 单窗推理中位约 80 µs，而帧间隔是 32 000 µs，实时因子约 370×；Smart Turn 对 4 秒语音段完整判定一次中位 68.2 ms，每轮一次，占轮次总延迟（网络 + TTS 通常以秒计）不到 1%。

还有一个架构层面的取舍：Realtime（端到端）模式下，支持服务端 VAD 的供应商自己判定 turn 结束，本地两级检测就退居二线，只在级联模式（ASR → LLM → TTS 三段自组）和不支持服务端 VAD 的线路上承担提交触发。别跟服务端抢方向盘。

## 二、回声：自问自答是最经典的死法

AI 从扬声器播报时，声音会被麦克风收回去。如果这段音频被转写成"用户发言"提交给模型，模型就会对着自己刚说的话滔滔不绝——**自问自答循环**，全双工语音助手的头号死因。

我们的防线有四道，从音频层到文本层逐层收窄：

1. **让浏览器 AEC 工作**：工作台对练时，麦克风采集和播报共用一个 WebAudio `AudioContext`，Chromium 的回声消除需要看到播放信号才能消回声，这个前提经常被忽略。
2. **播报期底噪追踪**：打断监听器在播报期间追踪"回声底噪"——窗口 RMS 取最小值缓慢上浮，每窗 2%（约 1.6 秒时间常数），另有约 500 ms 建底期只追踪不计数，避免播放起始的回声冲击被误判成人声。
3. **当轮回声判定**：全双工泵同时观察播报 PCM 和麦克风 PCM，用皮尔逊相关判定"这轮上行是不是刚才播报的延迟回波"，命中即不入轮。
4. **文本回声闸门（最后一道）**：定稿的用户转写与最近播报文本做归一化比对，命中即整轮丢弃。

第四道最有趣，因为它要回答一个刁钻的问题：**TTS 念的和 ASR 听到的往往不是同一串字符**。TTS 念「现在是2026年9月28日，星期一」，ASR 转写常是「现在是二零二六年九月二十八日星期一」。所以比对前先归一化：转小写、全角折半角、丢弃标点空白、中文数字换算成阿拉伯数字。判定规则写进了常量：

```rust
// src-tauri/src/services/echo_guard.rs
const ECHO_MIN_CHARS: usize = 6;      // 归一化后不足 6 字符不参与判定
const CONTAIN_MIN_CHARS: usize = 8;   // 双方 ≥8 字符且包含关系即回声
const DICE_ECHO_THRESHOLD: f64 = 0.85; // 字符 bigram Dice ≥0.85 即回声
```

阈值 0.85 是"取高不取低"的选择。真机实测里同句回声的 Dice ≥ 0.9，而用户真的在复述 AI 的话时——比如「没错就是2026年9月28日星期一」对「现在是2026年9月28日星期一」——Dice 约 0.84，必须放行。漏掉一条回声的代价是自问自答循环（前面三道防线会兜住绝大多数）；误吞一句真人确认的代价是用户被无视，且用户根本不知道为什么。两种错误不对称，所以阈值向"宁可漏过、交给上游"偏。

另外，哼声和单字应答（「嗯」「对」）归一化后不足 6 字符，直接豁免——它们永远不会被闸门误吞。

## 三、打断：AEC 会把真话也压低

播报期间用户插话（barge-in）听起来是个简单问题：检测到人声就停播。但真机实测给了我们当头一棒：**WebView 的 AEC 在播报期会把近端人声一起压低**——60% 满量程的合成人声在播报期的 Silero 概率只有 0.34~0.41，且在 0.31~0.77 之间高频抖动。纯概率阈值在双讲场景（AI 在说、用户也在说）永远打不断：调低阈值会把回声当打断，调高阈值真打断也漏。

解法是两路信号互补：

```rust
// src-tauri/src/audio/barge_in.rs（节选）
const TRIGGER_WINDOWS: usize = 8;   // 滑动窗：最近 8 窗 ≈ 256 ms
const TRIGGER_VOICED: usize = 6;    // 其中 ≥6 个人声窗即触发
const ENERGY_ASSIST_PROB: f32 = 0.3;   // 能量辅助：概率 ≥0.3 且
const ENERGY_ASSIST_RATIO: f32 = 3.0;  // RMS ≥ 底噪 3 倍也计为人声
```

- **滑动窗计数代替连续计数**：最近 8 窗内 ≥6 个人声窗即触发。为什么不用"连续 N 窗"？因为自然语音的词间空隙就能达到 1~2 个低概率窗，连续判定会被一个 0.3 以下的窗清零，手感是"怎么喊都喊不停"。滑动计数容忍这些空隙。
- **能量辅助判定**：概率不够、但窗口能量显著高于播报期回声底噪（≥3× RMS）时也计为人声。原理是回声窗的 RMS 贴着底噪走（底噪本来就是从回声追踪出来的），而人声叠加时能量跳变 3~20 倍，两者分得开。

触发后的动作链：清空播放缓冲（立即静音）→ 取消在途响应 → Realtime 模式按协议向服务端发取消/截断事件 → 从用户开口处继续收集音频进入新一轮。

效果有数字：离线评测里真打断 4/4 检出，**首次触发延迟中位 217 ms**（[评测报告](../reports/audio-eval.md)）；同一份报告也诚实地记录了短板——无 AEC 的合成回声场景下监听器会持续误触发，生产链路对回声的抑制依赖上游 AEC，数字代表"AEC 失效时"的风险敞口，而不是宣称"我们不怕回声"。

## 四、断了怎么接：一个真实的生产事故

端到端 Realtime 走 WebSocket 长连接，断线重连是标配能力。我们踩的坑是：**qwen 线路出现过"断连 → 重连 → 全量回放上下文 → 服务端把 AI 说过的话当新输入 → 重新生成 → 再断连"的死循环**——回放把 assistant 轮也发了回去，服务端把它当成需要回应的用户新发言，生成、播报、超时、断连，循环往复。

修复分两半（提交 `22bd2a2`）：

```rust
// src-tauri/src/providers/realtime_session.rs（节选）
const RECONNECT_BASE: Duration = Duration::from_millis(500); // 指数退避起点
const RECONNECT_CAP: Duration = Duration::from_secs(30);     // 退避封顶
const IDLE_RECONNECT_AFTER: Duration = Duration::from_secs(120); // 空闲主动重建
```

1. **回放时跳过 assistant 轮**：只回放用户输入，AI 的历史回答由模型在上下文里看到，而不是当作需要重新生成的输入；
2. **回放逐条确认**：每条 `conversation.item.create` 等服务端确认后再放下一条，而不是一把梭全量灌入——即使再断连，也知道回放到了哪里。

指数退避（500 ms 起步、翻倍、30 s 封顶）加空闲 120 s 主动重建，规避各家服务端不一致的空闲超时。重连期间麦克风输入在有界队列里继续积累，恢复后一次补上，用户不需要重说话。

## 五、工程上的几条心得

- **热路径不是瓶颈，状态机才是**。整条"摄入 → VAD → 分段/打断"路径的实时因子在 370× 以上，Silero 推理只占帧间隔的 0.25%。真正花时间的是分段器状态、打断监听状态、回声闸门状态之间的交互，以及每个阈值的取舍。
- **每层防线都要为"上一层失效"设计**。浏览器 AEC 不完全可控，系统 AEC 在虚拟声卡链路上不存在，所以文本层兜底永远保留；没有把宝押在任何单层上。
- **阈值要么有实测依据，要么标注为待验证**。0.85 的 Dice、3× 的能量比、8 窗 6 人声的滑动判定，全部写在常量注释里附实测出处；而句尾提交延迟（评测中位 2340 ms，高于 700 ms 静音设计值）这种我们还没调好的参数，评测报告里原样承认，不粉饰。
- **数字要能复现**。本文所有数据出自仓库里的 [Criterion 基准](../reports/benchmarks.md)与[离线评测](../reports/audio-eval.md)，语料确定性生成、跑生产代码、一条命令复现——这比"实测很快"有说服力得多。
