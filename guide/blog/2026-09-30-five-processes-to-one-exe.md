# 从五个进程到一个 exe：把 Electron + Go + Python 重构成 Tauri 的经验

> 本文是 RoleAI 技术系列的第三篇，讲这个项目的架构收敛史：它最初是一个 Electron + Next.js + Go + Python 的多进程系统，现在是单一 Tauri 2 应用。重构发生在 2026 年 8 月，本文是事后的复盘，决策记录见 ADR [0001](../adr/0001-single-tauri-app.md)。

## 起点：一条"标准"的 AI 应用架构

RoleAI 的前身是一个 AI 面试助手，2026 年 8 月 10 日的首提交（`c78cedd`）导入的就是这条多进程产品线，随后一周内陆续加入了 Go Control API、RTC 音频桥等组件。当时的架构在 AI 应用里非常"标准"：

- **Electron + Rust 客户端**：界面与本地能力；
- **Next.js 管理端**：配置与管理界面；
- **Go Control API**：会话编排与业务逻辑中枢；
- **Python Agent**：AI 能力（语音、LLM 调用）；
- **数据库 + nginx**：状态与网关。

每个进程单独看都合理——Go 写 API 快，Python 生态对 AI 友好，Next.js 管理端开箱即用。但对一个**本地优先的语音助手**，这条链路有致命问题。

## 为什么要收敛：三个每天都付的代价

**第一，用户要跑 4~5 个进程才能得到一次语音回答。** 任何一环挂掉，用户看到的现象都是"连不上"，而不是一个可解释的错误。排障变成逐进程检查：Python Agent 活着吗？Go API 起了吗？数据库连接正常吗？对一个发给普通用户的桌面应用，这是不可接受的。

**第二，部署要装数据库、配服务、起网关。**"本地优先"名存实亡——数据确实在本地，但形态是一个小型的服务端部署。安装文档有一页半，而它本该是"双击安装包"。

**第三，每条进程边界都是一次序列化、一个故障点、一份配置。** 语音链路上的音频帧要跨进程传输，热路径上多一层 IPC 就多一分延迟和抖动；配置散落在各进程，改一个字段要同步三处。

## 为什么是 Tauri，而不是"Electron 单进程"

收敛的方案候选有三个：

1. 保留多进程，修补可靠性——继续背着部署与联调成本，只是把故障隐藏得更好；
2. 收敛为单一 Tauri 2 应用——Rust 承载全部业务，WebView 只跑界面；
3. Electron + Node 单进程重写。

排除方案 1 不需要论证。方案 3 败在一个具体的技术判断上：**这个应用的核心是音频实时处理**——Silero VAD 要每 32 ms 窗推理一次，PCM 泵要持续搬音频帧，打断检测要统计滑动窗。这些负载在 Node 的事件循环模型里做不好：GC 停顿、事件循环被 UI 任务抢占，都会直接变成音频卡顿。Rust 没有运行时 GC，音频线程可以做到确定性的调度。

于是是方案 2：Tauri 2。WebView（Windows 上是 WebView2）负责界面，Rust 主进程承载会话编排、音频管线、Provider 适配、资料库、凭据——全部业务。

## 怎么迁：逐页面阶段迁移，每阶段有验收

大规模重构最大的风险是"停机重建"——分支拉出去三个月，合回来世界已经变了。我们用的方法是**按页面逐阶段迁移**：壳层 → 设置 → 资料 → 级联会话 →……每个阶段有明确的验收记录，验收过了才切下一阶段；没迁完的页面继续跑旧链路。

这件事能成立的前提是旧链路一直保持可用。回头看，这条纪律救了我们不止一次：迁移期间的每个 bug 都能立刻分辨"是新代码的问题还是老问题"，因为新旧链路是并存可对比的。

最终 Go Control API、Python Agent、Next.js 管理端、登录体系全部移除，仓库只剩一条 Tauri 产品路径。

## 收敛之后：三个新问题

架构收敛不是终点，它把复杂度从进程间搬到了进程内，产生了三个新问题，各有一个工程化解法。

**问题一：Rust 和 TypeScript 之间的类型契约。** 以前跨进程通信靠 API schema，现在只剩 Tauri IPC 一条缝——缝小了，但类型不一致的坑还在：Rust 侧改一个字段名，前端拿到 `undefined` 才发现。解法是 [ts-rs](https://github.com/n/ts-rs)：Rust DTO 上标注 `#[derive(TS)]`，`cargo test` 时自动生成 `src/generated/bindings.ts`，前端直接 import 这些类型。字段改一边，编译失败。生成文件禁止手改，并有契约测试锁定 IPC 命令面不可膨胀。

**问题二：不是所有本地能力都适合塞进 Rust。** 会议音频采集需要 WASAPI 进程环回（loopback），在纯 Rust 里做稳妥的进程环回采集，生态不成熟。解法是保留**一个**子进程：C# AudioBridge，复用 MIT 许可的 NAudio.Wasapi，通过一条极简的帧协议（音频帧 / clear 打断清空 / drain 播净回执）与主进程通信，发布产物自带 .NET 运行时。收敛不等于教条——该留的进程留着，但把它钉死在"单一职责 + 极简协议"上。

**问题三：怎么防止架构再次腐化。** 多进程时代腐化的信号是"又加了一个服务"；单进程时代的信号是"IPC 面悄悄变宽、能力白名单悄悄变大"。解法是把不变量钉进测试：安全面基线测试把能力白名单、IPC 命令面等关键文件的哈希固定在一个 JSON 里，任何漂移直接红测；另一组契约测试保证前端只有 `src/api/commands.ts` 一个文件能碰 Tauri IPC。今天的 README 契约测试甚至检查文档——README 只许描述单一 Tauri 产品路径，谁在文档里复活旧架构的描述，CI 会红。

## 验收：数字

架构收敛的收益最终要落在数字上：

- **一个安装包**。`npm run tauri:build` 产出单一 NSIS 安装包；打包冒烟测试在隔离环境启动打包后的 exe，**断言进程树里没有 Node、Go、Python、PostgreSQL 或 Nginx**，安装目录没有混入配置、数据库、日志——这条断言本身就是架构承诺的机器可验证形式。
- **音频热路径与 UI 同进程**。Criterion 基准显示整条"摄入 → VAD → 分段/打断"路径实时因子约 370× 以上（Silero 单窗推理约 80 µs / 32 ms 帧），不再有跨进程序列化。
- **测试规模**。收敛后单一代码库承载 700+ 个 Rust 单元测试、400+ 个前端测试用例（vitest）、32 个 Node 契约测试，一条命令全量门禁。
- **运维面**。无数据库安装、无服务编排、无网关配置；密钥进 Windows 凭据管理器，数据全在本机 SQLite。

## 复盘：三条带走的经验

**1. "每进程一个理由"不是架构风格，是成本核算。** 当年引入 Go 和 Python 的理由（生态、开发速度）都是真的，但没人核算"用户多跑一个进程"的成本。桌面产品的部署成本是用户付的，而用户的耐心比工程师的少得多。

**2. 重构的顺序比范围重要。** 逐页面迁移、每阶段验收，让风险始终被限制在"一个页面"的尺度内；反过来，如果一开始就定"三个月后全部切完"，大概率烂尾。

**3. 架构承诺要变成测试。** "我们是单一 Tauri 应用"是一句话；打包冒烟断言进程树、安全面基线哈希锁定、README 契约，是把这句话变成 CI 里会红的测试。人对承诺的记忆会衰减，测试不会。
