# 在桌面应用里做本地 RAG：SQLite + sqlite-vec 混合检索实践

> 本文是 RoleAI 技术系列的第二篇。RoleAI 是一个本地优先的 Windows 实时语音 AI 助手，用户把简历、岗位 JD、产品资料导进本地知识库，会话里的 AI 就能引用这些内容回答。文中评测数据均可在仓库一键复现，测试环境见[基准与评测报告](../benchmarks.md)。

## 先回答一个问题：要不要装向量数据库？

做桌面应用的 RAG，第一个诱惑是上"正经"向量数据库：独立进程、gRPC、ANN 索引，样样专业。但对一个"安装即用、数据不出本机"的桌面应用，独立向量数据库意味着：

- 用户要多装一个服务，出问题时报"连不上"而不是可解释的错误；
- 数据库文件、端口、生命周期都要应用托管；
- 向量数据和业务数据（资料、会话、纪要）分属两个存储，事务一致性自己拼。

RoleAI 的选择是：**SQLite 一口锅端**。全文检索用 SQLite 内建 FTS5 虚拟表，向量检索用 [sqlite-vec](https://github.com/asg017/sqlite-vec) 扩展的 vec0 虚拟表，业务表和这两张表在同一个数据库文件里，备份恢复一份文件全搞定。这个决策的完整推理在 ADR [0003](../adr/0003-sqlite-sqlite-vec.md)，本文讲落地细节和评测结果。

## 表结构：两路召回，一个事务

资料入库时分块，每块写三处：`material_chunks`（原文与元数据）、`material_chunks_fts`（FTS5 全文索引）、`material_chunk_vectors`（vec0 向量）。前两处在同一事务里提交；向量一路是可选的——用户可能不配 Embedding 服务，没配时 FTS 照常工作，配了之后自动补索引。

两个容易踩的坑，我们都做进了设计：

**嵌入空间指纹。** 用户中途更换 Embedding 供应商或模型是常态，但两套嵌入空间的向量不能混着检索。向量表按 Embedding 配置的指纹（供应商、模型、维度、是否归一化）管理——换了配置、维度对不上，自动重建向量表，而不是拿 A 家的查询向量去搜 B 家的资料向量，那种错误不报错、只是悄悄变蠢。

**状态门槛。** 资料有生命周期：`text_ready` / `vector_ready` 才参与检索，正在删除的先标记 `deleting` 并屏蔽检索、再物理删除。否则会出现"刚点了删除还能搜到"或"删到一半检索报错"。

## 分块：为简历和文档设计，而不是为论文

分块器版本 `resume-semantic-v1`，常量即设计：

```rust
// src-tauri/src/materials/chunk.rs（节选）
pub const CHUNKER_VERSION: &str = "resume-semantic-v1";
pub(crate) const MAX_CHUNK_RUNES: usize = 2000;  // 单块上限
const HARD_SPLIT_LOOKBACK: usize = 400;          // 硬切时回看 400 字符
const MAX_CHUNKS: usize = 500;                   // 单份资料最多 500 块
```

策略是先按章节标题语义切分（「工作经历」「项目经验」「教育背景」这类比正则更可靠的语义边界），超长段落再按窗口硬切，回看 400 字符避免句子在边界被腰斩。每块记录来源资料、章节名、起止字符位置——检索命中后能定位回原文做证据引用，这是"AI 回答带出处"的基础。

解析器版本和分块器版本一起记录在资料行上：未来升级分块算法，旧资料能被识别出来按需重建，而不是全体静默重跑。另外，每份资料按内容 SHA-256 建指纹，同一份文件重复导入直接返回已有记录的 ID，磁盘上永远只有一份副本。

## 融合：RRF 的好处是不用调权重

两路召回怎么合成一个排序？常见做法是加权：`score = 0.4 × keyword + 0.6 × vector`。但关键词得分（BM25 量级）和余弦相似度（0~1）量纲不同，权重全凭感觉调，换个语料就得重调。

RoleAI 用倒数排序融合（Reciprocal Rank Fusion）：每路候选按**名次**打分 `1 / (60 + rank)`，同一块的得分相加：

```rust
// src-tauri/src/materials/hybrid.rs（节选）
const CANDIDATE_K: u32 = 20;   // 每路取前 20 条候选
const RRF_K: f64 = 60.0;

fn reciprocal_rank_fusion(
    fts: Vec<MaterialSearchHit>,
    vectors: Vec<MaterialSearchHit>,
) -> Vec<MaterialSearchHit> {
    let mut scores = HashMap::<String, f64>::new();
    let mut hits = HashMap::<String, MaterialSearchHit>::new();
    for (rank, hit) in fts.into_iter().enumerate() {
        *scores.entry(hit.chunk_id.clone()).or_insert(0.0) += rrf_score(rank);
        hits.entry(hit.chunk_id.clone()).or_insert(hit);
    }
    for (rank, hit) in vectors.into_iter().enumerate() {
        *scores.entry(hit.chunk_id.clone()).or_insert(0.0) += rrf_score(rank);
        hits.entry(hit.chunk_id.clone()).or_insert(hit);
    }
    // ……按融合分排序返回
}

fn rrf_score(rank: usize) -> f64 {
    1.0 / (RRF_K + rank as f64)
}
```

名次融合对量纲天然免疫：第 1 名就是 1/60，不管这 1 分来自 BM25 还是余弦。RRF_K=60 是原论文的经验值，我们没有再调——调它需要标注数据，而我们的离线评测集（50 题）规模还撑不起这种细调，与其凭感觉调参，不如把参数固定在文献默认值上，把诚实的不确定性写进文档。

命中后还有一个生产细节：**相邻块合并**。金标内容经常横跨两块，把同资料相邻命中的块合并返回，比单独返回碎块更接近"引用一段原文"的真实需求。

## 评测：一次把黑盒打穿

方法论先行：我们给检索做了一套**离线评测集**——10 篇虚构产品资料（每篇约 350–450 字）、50 个自然语言问题，每题标注金标资料与金标段落（[评测报告](../reports/rag-eval.md)）。指标是 Recall@1/3/5 和 MRR，"块级命中"要求命中块**包含**金标片段，标准很严格。

向量一路用的是**字符 bigram 哈希嵌入替身**（128 维、L2 归一化）——它不是语义 Embedding，这一点必须先说清楚。用替身的原因是：评测要确定性、离线、零成本、可复现，而替身能回答的问题是"**检索机制本身工作正常吗**"，不是"语义检索质量多高"。

50 题的结果：

| 模式 | R@1 | R@3 | R@5 | MRR |
| --- | ---: | ---: | ---: | ---: |
| keyword（FTS5） | 2% | 2% | 2% | 0.02 |
| vector 替身 | 62% | 70% | 84% | 0.69 |
| hybrid（生产路径） | 62% | 70% | 84% | 0.69 |

三个发现，一个比一个有意思：

**1. 关键词路径对自然语言整句几乎完全失效（2%）。** 根因是 FTS5 trigram 分词 + 停用词切分后的 AND 短语要求每个子串逐字出现，整句问法与资料原文的措辞稍有差异就零命中。这不是要修的缺陷，而是路径定位：关键词一路服务的是"精确术语短查询"（贴一个报错码、搜一个产品型号），自然语言问句必须靠向量一路。知道每条路擅长什么，比追求单一万能检索更实际。

**2. 替身拿到 R@5 84% 说明机制是通的。** 替身本质是"抗分词的字符级词汇匹配"，它没有语义理解能力，所以 84% 全部来自字面重叠——这恰好证明了 SQLite vec0 近邻检索、RRF 融合、相邻块合并这些**机械环节**都在正确工作。换成真实 Embedding 后语义泛化只会更好，但好多少，要等配置了在线服务的评测来回答，报告里不做任何推断性数字。

**3. hybrid 与 vector 完全一致。** 在替身设置下关键词一路几乎不贡献候选，RRF 退化为单路。这与发现 1 自洽，也预示了真实 Embedding 下两路的互补性会恢复（精确词靠关键词，同义改写靠向量）——但同样，等在线评测验证。

## 性能：桌面规模下 SQLite 绰绰有余

Criterion 基准（[报告](../reports/benchmarks.md)）给了量的底气：

- 4904 块规模混合检索中位 **0.48 ms**（关键词 + 64 维向量 RRF 融合，top 5）；关键词一路 52.7 µs，几乎不随规模增长（FTS5 倒排索引）；
- 484 块小库混合检索 256.7 µs；
- 单篇 1 万字资料落库（材料行 + 全文 + 分块 + FTS，单事务）3.99 ms；
- 向量索引写入约 23–26 千块/秒。

对一个"个人资料库几百到几千块"的桌面场景，检索在整轮 1–5 秒的对话延迟里完全无感。独立向量数据库在这个量级的优势（十亿级 ANN、分布式）根本用不上，而它带来的部署复杂度是每天都付的。

## 备份与恢复：假设恢复会失败

最后一个工程细节：备份用 SQLite 在线备份 API 把数据库完整复制到归档目录，不停会话；**恢复则假设自己会中途失败**——先写回滚文件（`.restore-rollback`）与恢复日志（`.restore-journal.json`），再执行恢复，任何一步失败都能回滚到恢复前状态，不会把用户现有数据库切成两半。备份产物是标准 SQLite 文件，用户可以用任何工具打开检查——数据是用户的，格式不该是门槛。

## 小结

- 桌面应用的 RAG，SQLite + FTS5 + sqlite-vec 一口锅端：零部署、单文件备份、事务一致，性能在桌面规模下毫秒级；
- RRF 融合免调权重，把参数固定在文献默认值，把调参冲动留给有标注数据的时候；
- 评测要区分"机制验证"和"质量评测"：哈希替身回答前者，永远不要用替身数字暗示后者；
- 让每条检索路径待在它擅长的场景里（精确术语 → 关键词，自然语言 → 向量），比追求单一万能检索靠谱。
